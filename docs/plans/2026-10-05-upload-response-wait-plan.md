# An upload answer that never comes is a stall (#40)

**Decision (Jake, 2026-10-05, "so fix it"):** once an upload's body has been handed over in full, IA's answer must arrive within 120 s; otherwise the request is dropped (closing the connection) and sent again at once, spending one of `--retries`, exactly as a dead send does. No flag.

**The measurement.** Jake ran the probe (`upload-response-latency-probe.fish`, 2026-10-05) against `s3.us.archive.org`: five part PUTs of 1 KiB on a fresh `test_collection` item, each with `Content-MD5`, timed from the last body byte to the first response line: 6240, 3890, 1850, 4335, 1786 ms (median 3.9 s, max 6.2 s). The variance on a kilobyte says the wait is IA's backend, not hashing.

**Why 120 s.** The Python `internetarchive` library, which has carried multi-GB single PUTs to IA for years, sets `timeout=120` on `upload_file` (requests' timeout, so 120 s to the response headers after the body); `ia-core` keeps that number. It is twenty times the largest wait measured on a part, and leaves room for IA's post-body work on a large single PUT. A knob would need a reason a user could act on; there is none (the answer comes from the same endpoint whatever the client does), so it is a fixed rule like the 60 s dead-send rule.

**Where.** `BodyWatch` already knows the moment the body is done (the `done` flag, set when the byte count reaches the body length or the stream ends). It records that instant; `check` then has two verdicts, a send that moved no bytes for the window (as before) and an answer that has not arrived `RESPONSE_WAIT` after the body; `watch_send` returns `SendEnd::Unanswered { wait_secs }` for the second. The two call sites (`retry::send_with_retry` for every multipart request, `single::upload_file` for the single PUT) treat it as a stall: re-send at once while the budget lasts, past it `IaError::UploadStalled`. The transport keeps no read timeout (its clock is not reset by body writes).

**Not judged:** a request with no body stream to watch (initiate, complete, abort, listings never call `wrap`; nothing starts their clock), and reading a response body (the bound is on the answer's headers; `send()` resolves when they arrive, and the later `text()` reads run on the transport with no read timeout). A zero-length body is done at `wrap`, before the connect, so its 120 s runs from there; the 30 s connect timeout fits inside it. "After the body" means after the transport took the last chunk: hyper's write queue and the kernel's send buffer (up to about half a megabyte together) still drain inside the 120 s, so an uplink under a few KB/s is judged unanswered on every attempt, while the dead-send rule's floor is about 1 KiB/s. #40's scope is the wait after a body.

**The error.** `UploadStalled` gains `response_secs: u64` and `unanswered: usize`; `stalls` still counts every stall, `unanswered` the ones that were an unanswered body. The text keeps its shape, "upload of <item>/<key> stalled N times: <detail>", with the detail from `stall_detail`: "no bytes were sent for 60 s" (no unanswered), "no answer came within 120 s after the body was sent" (all unanswered), or "2 sends moved no bytes for 60 s and 1 answer did not come within 120 s after the body was sent" (mixed). The multipart part message uses the same detail: "part N of M stalled K times (<detail>, after A attempts): multipart upload <id> is kept ...", which changes its dead-send wording from "no bytes sent" to "no bytes were sent" (user-visible text since 0.21.0). `--json`'s `upload_stalled` carries both new fields. `#[non_exhaustive]` on the enum does not stop an external crate from constructing or exhaustively destructuring this variant, so the two fields are a break for any crate that does; `ia-core` is `publish = false` and `ia-cli` never names the variant, so the practical impact is nil, and the version bump stays with the release process.

**Test seam.** `stall::response_wait()` returns `RESPONSE_WAIT` (120 s), or the wait of a live `PolicyOverride::with_response_wait` under `cfg(test)`; `shrink_policy()` sets window 2 s, grace 1 s, wait 4 s, so a test can tell the two rules apart (a 3.5 s answer is past the window and within the wait). A new fixture, `silent_listener`, reads every byte it is sent and never answers.

## Review (2026-10-05), closed before merge

Important, taken: clippy failed on the lib build because both call sites matched the two dead verdicts together and read the seconds from the policy, leaving `SendEnd`'s fields unread; each arm now takes its value from the verdict that fired (and the `_` wildcard went with it). Zero-length bodies were judged (the clock starts at `wrap`) while three documents said they were not; the code stands, the documents say so, and `a_zero_length_body_is_done_at_wrap_and_its_wait_runs_from_there` pins it.

Suggestions, taken: the test hook made the response wait equal to the window, so the 3.5 s-delay test had been cut to 1.5 s and no longer proved a finished body escapes the dead-send rule; `PolicyOverride::with_response_wait` gives the wait its own value (4 s) and the 3.5 s delay is back. `done` plus `done_at` under a mutex became one `OnceLock<Instant>`. The buffered-bytes caveat is in the module doc, usage.md and above. "of the body" became "after the body was sent" in every message, help and doc. The plan's claim that external construction was impossible was wrong; corrected above.

Noted: the bound is on the answer's headers, not on reading a response body (above); the reviewer verified from the reqwest 0.13.2 source that `send()` resolves on the head. The multipart part wording change is recorded above. The Python library's `timeout=120` was checked against `internetarchive/item.py` on GitHub (`upload_file`, `request_kwargs['timeout'] = 120`).
