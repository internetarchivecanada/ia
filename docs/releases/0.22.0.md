# ia 0.22.0

Released from tag `v0.22.0`. Covers everything merged after `v0.21.1`:
PRs #59, #63 and #68 (issues #21 and #62). `ia-core` and `ia-cli` are
both 0.22.0; the library is still pre-1.0. The minor bump is for the
`ia-core` signature change below.

## Fixed

- **`ia upload --multipart --no-derive` queued a derive** (#62, PR #63).
  The multipart completion request is what creates the task that writes
  the object, and it carried only `x-archive-keep-old-version`; the
  `x-archive-queue-derive: 0` sent on the initiate request did not reach
  it. The derive task that followed went to `wait_admin` and blocked the
  item's queue. The completion request now carries the same item-level
  headers as the single PUT: `x-archive-queue-derive` (`0` with
  `--no-derive` or on a file that is not the last, `1` on the last file),
  `x-archive-keep-old-version` (`1` unless `--no-backup`),
  `x-archive-auto-make-bucket` and the metadata headers on the first
  file, `x-archive-size-hint`, and the `--header` values other than
  `Content-Type` and `Content-Length`. The initiate request carries the
  same list. A resumed upload, which sends no initiate request, carries
  the list on its completion request. Verified on IA: the
  `s3-put-complete-multipart` task carries `no_derive: 1` and no derive
  follows.

## Added

- **A single PUT that dies continues as a multipart upload** (#21,
  PR #59). Multipart stays off by default. When the single PUT of a file
  larger than 2 MiB ends in a dead send, an unanswered body or a
  transport error, and at least one retry is left, the file continues as
  a multipart upload with the retries it has not spent, and every file
  larger than 2 MiB that starts afterwards in the same run is sent as
  multipart from the beginning. Files of 2 MiB or less are always single
  PUTs. A 503 throttle, a non-retryable S3 refusal and a spam rejection
  do not switch. `--multipart` still forces multipart for every file.
- **A rerun resumes a switched file without `--multipart`.** At the
  start of a run, `upload` asks IA once per item for the item's
  unfinished multipart uploads (the listing `ia upload cleanup` shows). A
  file whose name has an unfinished upload is sent as multipart, whatever
  its size, and resumes from the parts IA holds after the usual check
  against the local file. No listing with `--multipart` or `--dry-run`.
  The listing gets the run's retry budget and 120 s in all; a listing
  that fails does not fail the item: the run warns and sends single PUTs.
  The part-failure message now reads "rerun the same command to resume".

## Changed

- `ia-core`: `multipart::complete_upload` takes
  `extra_headers: &[(String, String)]` in place of `keep_old_version:
  bool`, as `initiate_upload` does.
- `ia-core`, additive: `upload::MultipartFallback` (`is_on`,
  `has_unfinished`), `UploadOpts.multipart_fallback`,
  `UploadOptsBuilder::multipart_fallback`,
  `upload::MULTIPART_FALLBACK_MIN_SIZE`.
- `ia-core`, behavior with `multipart` false: `upload_item` sends one
  listing request per item before the first file (not under `dry_run`);
  a file larger than 2 MiB may be uploaded as multipart after a dead,
  unanswered or transport-failed single PUT, and may then leave an
  unfinished multipart upload on IA if it fails; `UploadResult.retries`
  for that file includes the single PUT's attempts; a `warn` event is
  emitted when the listing fails; a first file on an unreachable host
  fails from the listing request rather than from the single PUT. There
  is no library-level opt-out.

## Dependencies

- rust_xlsxwriter 0.79 to 0.101 and calamine 0.36 to 0.37, which move
  zip to 9.0.5, closing RUSTSEC-2026-0367, 0368 and 0369;
  rustls-webpki 0.103.16 and webpki-root-certs 1.0.10, closing
  RUSTSEC-2026-0382 and 0383 (PR #68).

## Known follow-ups

- #60: multipart control requests (initiate, complete, abort, listings)
  carry no body, so neither the dead-send rule nor the 120 s answer
  bound applies to them.
- #64: multipart listing keys are not XML-unescaped, so a file name
  with `&` never resumes.
