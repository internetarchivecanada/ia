# ia 0.23.0

Released from tag `v0.23.0`. Covers everything merged after `v0.22.0`:
PRs #70, #71, #72, #84 and #85. `ia-core` and `ia-cli` are both 0.23.0;
the library is still pre-1.0. The minor bump is for the new `IaError`
variants and the new `ia update` behavior below.

This is the first release whose assets ship with `SHA256SUMS` and a
build provenance attestation, and the first whose `ia update` checks
what it downloads. A 2026-10-22 dependency and supply-chain audit of
the repository, prompted by the eMudhra intermediate-certificate
compromise, found no exposure to that incident: every released binary
verifies TLS against the operating system's trust store and bundles no
root certificates. The rest of this release is what that audit did
turn up.

## Added

- **`ia update` is in every binary** (PR #70). The command used to exist
  only in binaries built with a `self-update` feature that only the
  release workflow enabled, so a `cargo install --path ia-cli` build
  lacked it. The feature gate is gone.
- **Releases carry `SHA256SUMS` and a provenance attestation** (PR #84).
  The release job writes `SHA256SUMS` over every asset and attaches it,
  and records a build provenance attestation through GitHub's Sigstore
  integration. `sha256sum --ignore-missing -c SHA256SUMS` checks a
  download; `gh attestation verify <asset> --repo internetarchivecanada/ia`
  confirms it was built by this repository's release workflow. The
  README install example shows both.
- **`ia update` refuses an asset that does not match `SHA256SUMS`**
  (PR #85). Before installing, the updater fetches the release's
  `SHA256SUMS`, hashes the downloaded asset, and compares. A mismatch is
  `update_checksum_mismatch` and nothing is written next to the running
  binary. From 0.23.0 on, a release without `SHA256SUMS`, or without a
  line for this platform's asset, is `update_checksum_missing` and
  nothing is downloaded. Releases older than 0.23.0 were published
  without the file; `ia update install` still installs them, with a
  warning on stderr. Binaries older than 0.23.0 keep updating without
  this check until they are replaced.

## Changed

- `ia-core`: `IaError` gains `UpdateChecksumMismatch { asset, expected,
  actual }` and `UpdateChecksumMissing { version, asset }`, both
  permanent (never retried), with JSON codes `update_checksum_mismatch`
  and `update_checksum_missing`. Code that matches `IaError`
  exhaustively must add the two arms.
- `ia-core`, additive: `update::download_asset_checked`,
  `update::expected_checksum_for`, `update::parse_sha256sums`,
  `update::ExpectedSha256` (non-exhaustive, with `new`),
  `update::MIN_CHECKSUMMED_VERSION`, `update::SHA256SUMS_ASSET`.
  `update::download_asset` keeps its signature and stays unchecked.
- `ia config login` prompts for the password on the terminal device
  rather than on stderr (rpassword 7). Output on stdout is unchanged.

## Dependencies

- A full `cargo update` of 177 crates (PR #71), including reqwest
  0.13.5, hyper 1.12.0, tokio 1.54.1, rustls-platform-verifier 0.7.1 and
  rustls-native-certs 0.8.5. rpassword 5.0.1 to 7.5.4 closes
  GHSA-2p6r-x3vv-xqm2 (partial password reveal when the prompt is
  interrupted). anyhow 1.0.104, lru 0.18.5 and rand 0.9.3 or later close
  RUSTSEC-2026-0190, 0253 and 0097, none of which were reachable from
  this code.
- `aws-lc-rs` becomes a direct dependency of `ia-core` for SHA-256. It
  was already compiled in as rustls's crypto provider, so no new code
  is in the binary.

## Build and release process

- Every GitHub Action in the workflows is pinned to a full commit SHA,
  every cargo command runs with `--locked`, the advisory scan has its
  own workflow that also runs weekly, and Dependabot keeps the crate
  lock and the action pins current (PR #72).

## Known follow-ups

- `ia update` verifies the checksum, not yet the attestation. Verifying
  the attestation inside the binary needs a Sigstore client and a
  key-rotation policy; it is a separate change.
- #60: multipart control requests (initiate, complete, abort, listings)
  carry no body, so neither the dead-send rule nor the 120 s answer
  bound applies to them.
- #64: multipart listing keys are not XML-unescaped, so a file name
  with `&` never resumes.
