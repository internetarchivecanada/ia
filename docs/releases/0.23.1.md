# ia 0.23.1

Released from tag `v0.23.1`. Covers everything merged after `v0.23.0`:
PRs #88, #89, #90, #91, #92, #93, #94, #95, #101 and #102 (issues #60,
#61 and #64). `ia-core` and `ia-cli` are both 0.23.1; the library is
still pre-1.0. The patch bump is because no public `ia-core` type or
signature changes; the behavior changes are listed below.

Like 0.23.0, the release assets ship with `SHA256SUMS` and a build
provenance attestation. `ia update` from 0.23.0 checks the downloaded
asset against `SHA256SUMS` before installing it.

## Fixed

- **A file name with `&`, `<`, `>`, `"` or `'` never resumed a multipart
  upload** (#64, PR #91). IA-S3 escapes text in its XML answers, so
  `a&b.bin` is listed as `a&amp;b.bin`, and the listing parsers returned
  the escaped form. `--multipart` started a fresh upload of such a file
  and left the old one on IA; the per-item listing at the start of a run
  did not see its unfinished upload, so a rerun sent it as a single PUT;
  `ia upload cleanup` printed the escaped name and `--abort` built its
  URL from it; an escaped next-page marker requested the wrong page.
  Every field read from an IA-S3 listing or error answer is now
  XML-decoded (the five predefined entities and numeric character
  references), so the file resumes and `ia upload cleanup` shows the
  real name. Upload IDs are percent-encoded in the URLs that carry one
  (part PUT, complete, abort, list parts), so a decoded ID with `&` no
  longer splits the query string.
- **A multipart control request could wait forever for an answer** (#60,
  PR #94). The 120 s answer bound applied only to requests with a body
  stream, the single PUT and the part PUT. The multipart initiate,
  complete and abort requests and the upload and part listings had no
  clock of their own (the per-item listing at the start of a run already
  had 120 s over all its attempts), and a server that accepted the
  connection and sent nothing held them indefinitely. Since 0.22.0 an
  initiate follows a dead single PUT on the default path, so this could
  hang an upload that never asked for multipart. Every multipart request
  now has the bound: a request without a body stream counts as sent once
  it is handed to the transport, and an answer that does not come within
  120 s is abandoned and the request re-sent, spending one of
  `--retries`. Past the budget the failure is
  the existing stalled-upload error, counted as unanswered. Stall
  messages now say an answer did not come "after the request was sent"
  rather than "after the body was sent", here and in the `--retries`
  help; the JSON fields are unchanged.
- **The User-Agent omitted the S3 access key** (#61, PR #90). The Python
  library includes it, and archive.org uses it to attribute traffic to
  an account. The User-Agent is now
  `ia/{version} ({os} {arch}; N; en; {access_key}) Rust/{rust_version}`
  when an access key is configured (including through
  `IA_ACCESS_KEY_ID`), and unchanged without one. A key that is empty or
  contains characters unsafe in a header comment is left out.
  `ia config login`, which runs before credentials exist, and
  `ia update` stay keyless.

## Changed

- `ia-core`, behavior: `IaClient`'s User-Agent includes the configured
  access key as above. `IaError::UploadStalled` and the stall warnings
  use the "after the request was sent" wording. Multipart initiate,
  complete, abort and listing requests whose answers do not come within
  120 s are re-sent, and fail with `IaError::UploadStalled` once
  `--retries` (the `retries` budget) is spent. The public parsers
  `multipart::parse_initiate_response`,
  `multipart::parse_list_uploads_response`,
  `multipart::parse_list_parts_response` and `s3_error::parse_s3_error`
  return XML-decoded text. No public types or signatures change.

## Dependencies

- `quick-xml` 0.42 becomes a direct dependency of `ia-core` for the
  XML decoding (PR #91). It was already compiled in through `calamine`,
  so one copy is still built.
- Major crate updates: base64 0.23 (PR #89), json-patch 4 (PR #92),
  clap_mangen 0.3 (PR #93), comfy-table 8 (PR #95), sha1 0.11 (PR #101)
  and md-5 0.11 (PR #102). Behavior is unchanged. sha1 and md-5 move to
  digest 0.11; the hash strings they produce are the same. Table output
  is byte-identical. In the generated man pages, the SYNOPSIS line of
  `ia-cli-collection-create.1` and `ia-cli-status.1` lists the required
  option (`-C|--collection`, `--joblog`) after the optional flags rather
  than first; every other page is unchanged.

## Build and release process

- GitHub Actions move to their current majors, still pinned to full
  commit SHAs (PR #88): actions/checkout 7.0.1, actions/upload-artifact
  7.0.2, actions/download-artifact 8.0.2, softprops/action-gh-release
  3.0.3 and actions/attest-build-provenance 4.2.2. This is the first
  release built and published with them.

## Known follow-ups

- `ia update` verifies the checksum, not yet the attestation. Verifying
  the attestation inside the binary needs a Sigstore client and a
  key-rotation policy; it is a separate change.
- Reading the body of an IA-S3 answer, once its headers have arrived, is
  still unbounded (the initiate's upload ID, listings, error bodies). A
  bound there needs its own retry rule, because a re-sent initiate after
  IA answered creates a second upload.
- The completion request of a multipart upload is held to the same
  120 s. How long IA takes to answer a completion with hundreds of parts
  has not been measured; a slower answer is re-sent, and a re-send after
  IA accepted the first goes through the existing `NoSuchUpload` check.
